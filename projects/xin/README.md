> **Xin (辛)** blocks ads for the *whole machine*, not just one browser. The rule
> container, the compiler that builds it, the matcher that queries it and the
> local HTTP API in front of it are all implemented from scratch in **StarC** —
> no gcc, no Python, no Node, no third-party library, no proxy server, no cloud
> dependency at runtime.
>
> This is the first product built on the StarC toolchain.

---

## 1. What it actually does

Ads almost always come from *separate domains* (`pagead2.googlesyndication.com`,
`pos.baidu.com`, …). So Xin attacks the problem at the DNS layer, before any
traffic exists:

```
          ┌─────────────────────── your machine ───────────────────────┐
          │                                                            │
          │  hosts (110,302 × "0.0.0.0")   ← layer 1: resolution dies   │
          │        ▲                                                   │
          │        │ generated by                                      │
          │  xin_hosts.sc  ◄── rules.qrb ◄── xin_pack.sc ◄── text      │
          │                        │                                   │
          │                        ├──► xin_core.sc   (query + bench) │
          │                        └──► xin_serve.sc  (127.0.0.1:8353)│
          │                                                            │
          │  browser extension            ← layer 2: removes the empty  │
          │  (Chrome / Edge, MV3)            containers + "广告" labels │
          └────────────────────────────────────────────────────────────┘

          any app on the machine → system resolver → 0.0.0.0 → ad never loads
```

**Layer 1 (network).** A `hosts` block of 110,302 entries. Every process on the
machine — browser, WeChat's embedded webview, Steam, a game launcher, a desktop
app with a banner — resolves those domains to `0.0.0.0` and fails. Nothing is
proxied; no traffic leaves the machine.

**Layer 2 (page).** An MV3 extension that deletes the leftover ad *containers*
and the little "广告" compliance labels, so you see a clean page instead of a
grey skeleton. This is cosmetic-only by design — see §5 for why that matters.

**Layer 3 (verdict API).** `http://127.0.0.1:8353/check?domain=…` returns
`BLOCK` or `ALLOW` in ~656 ns. It is a *query service*, not an enforcement
point: it does not proxy, does not intercept, does not phone home. It exists so
other local software (a future DNS proxy, a browser extension, your own scripts)
can ask the same engine.

## 2. The parts nobody else ships

| Component | What is unusual about it |
|---|---|
| **`.qrb` container** | Self-defined binary format. `XINR` magic, version, fixed 48-byte records, plus a cosmetic selector section appended after the domain table. Clients **parse nothing** at load time. |
| **`xin_pack`** | The compiler that turns sorted text into that container. 110k rules → 132 ms. |
| **Matcher** | Binary search over the fixed-size table, then a label-suffix walk (`a.b.c` → try `a.b.c`, `b.c`, `c`). Exact suffix semantics, **not substring matching** — so `ads.doubleclick.net` is blocked while `notdoubleclick.net` is allowed. |
| **MV3 immunity** | Because blocking happens at DNS, the extension needs no `webRequest` and no `declarativeNetRequest` rule budget. Chrome's Manifest V3 tightening — which forced uBlock Origin into a cut-down "Lite" edition — **cannot touch this design**. |
| **Language** | All of the above is `.starc` / `.staro`. The only external calls are `kernel32.dll` and `ws2_32.dll`. |

## 3. Quick start (Windows)

```bash
# 0) prerequisites: a StarC compiler + bash/coreutils
export STARC_CC=/d/starc/starcc_v13/starcc.exe

# 1) optional: pull an upstream seed list (not redistributed here)
bash scripts/fetch-rules.sh

# 2) build everything + self-test
bash build.sh
```

`build.sh` prints something like:

```
[1/5] normalize + sort domains
      domains = 110302
[4/5] pack rules -> data/rules.qrb
format version = 2 (V1.2.0)
domain records = 110302
cosmetic rules = 53
output bytes   = 5295423
[5/5] self-test
total   = 32
blocked = 21
allowed = 11
ns/query  = 656
qps       = 1500000
```

Then:

```powershell
# 3) apply the hosts block (needs an elevated shell — this is the one manual step)
powershell -ExecutionPolicy Bypass -File scripts\apply_hosts.ps1
#    -> APPLIED: block lines = 110302

# 4) start the local verdict API (leave it running)
.\dist\xin_serve.sc

# 5) load the extension
#    chrome://extensions -> Developer mode -> Load unpacked -> select .\ext
```

To undo everything:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\restore_hosts.ps1
```

## 4. Measured numbers

All figures below were produced on the author's machine (Windows x86-64). They
are measurements, not estimates.

| Metric | 69 rules (repo default) | **110,302 rules** |
|---|---|---|
| Pack time (text → `.qrb`) | < 10 ms | **132 ms** |
| Container size | 4,239 B | **5,295,423 B (5.1 MB)** |
| Lookup latency | 166–322 ns \* | **656 ns** |
| Throughput (single thread) | 3.0–5.6 M qps \* | **1.5 M qps** |
| Hit rate on the 32-domain fixture | 21/21 | **21/21** |
| False positives on the fixture | 0/11 | **0/11** |
| Hosts fragment | 69 lines | **110,302 lines / 2.97 MB** |

\* **Measurement caveat, stated up front:** the benchmark times 96,000 queries
with `GetTickCount`, whose resolution is 15.6 ms. For the small rule set the
whole run takes 16–31 ms, so those two figures are quantisation noise, not a
real 2× difference. Only the 110k-rule number (656 ns) is measured at a duration
where the clock granularity is negligible. A proper `QueryPerformanceCounter`
harness is **NOT IMPLEMENTED**.

Design target was "< 10 µs per lookup". Measured 0.656 µs — roughly **15× better
than the target**, because the container is pre-sorted and pre-sized.

## 5. Honest assessment

### 5.1 What is genuinely good

1. **Fast, and measurably so.** 656 ns per decision, single thread, no GC, no
   allocation per query. Reading 110k rules costs one `ReadFile`.
2. **Zero parsing at load.** The container is a sorted array of fixed 48-byte
   records. `qrb_count()` is literally one 4-byte read at offset 8.
3. **MV3-proof by architecture, not by workaround.** DNS does the blocking, so
   browser policy changes cannot break the block itself.
4. **Fully local.** No proxy, no telemetry, no account, no cloud at runtime. Pull
   the plug from the internet and blocking still works — it is a local file.
5. **Nothing third-party at runtime.** Only `kernel32.dll` / `ws2_32.dll`.
6. **Format ownership.** Upstream lists are *input*, never a dependency. If every
   upstream project dies tomorrow, the engine still runs on its own container.
7. **System-wide.** Not "a browser extension" — every process that uses the OS
   resolver is covered.
8. **Free and MIT.** No IAP, no ad-supported tier, no upsell.

### 5.2 What is clearly bad — no sugar-coating

1. **Windows only.** StarC's code generator emits PE32+ only. Linux and Android
   do not exist yet. The Android path additionally *requires* a Java/Kotlin
   `VpnService` shell — that is an Android framework constraint, not laziness.
2. **`hosts` is a decaying mechanism.** If a browser or app turns on DoH/DoT, or
   ships its own HTTPDNS, this layer is bypassed silently. WeChat already uses
   HTTPDNS for parts of its traffic. Within a few years this needs a real local
   DNS server or it will look "broken" on modern setups.
3. **First-party ads are out of reach.** Baidu's "推广" and NetEase's in-house
   placements live on the *same* domain as the content. Blocking them by domain
   would block the site. Only the selector layer can hide them, and selectors
   are brittle.
4. **Selector layer is a treadmill.** Every site redesign can break it. It is
   53 rules of whack-a-mole, permanently.
5. **No whitelist yet.** There is no `allow.qrb`. If a rule breaks a site you
   care about, your only options today are "edit the text list and rebuild" or
   "remove the whole block". That is a real usability hole.
6. **No auto-update.** Rules are a snapshot (2026-11-20). Newly created ad
   domains will not appear until someone re-runs the fetch + build. Distribution
   is designed but not automated.
7. **No installer.** Three manual steps: elevated hosts write, start a service,
   load an unpacked extension. "Download and double-click" does not exist.
8. **Extension is unpacked dev-mode.** Not in any store. Chrome will nag. Store
   review for ad blockers is hostile in general.
9. **Coverage is Chrome/Edge only** for layer 2. Firefox, 360, QQ Browser are
   not covered (different extension systems).
10. **The HTTP server is single-threaded and blocking.** One request at a time,
    `Connection: close`, fixed 4 KB request buffer. Fine for localhost probing;
    it would fall over under real concurrency.
11. **Absolute paths are hardcoded in the `.starc` sources.** v1.2.1 has no CLI
    arguments; `build.sh` rewrites the path into a scratch copy. Ugly, and the
    first thing a contributor will trip over.
12. **No test suite.** The "fixture" is 32 hand-written domains plus a benchmark
    loop. There is no CI, no regression harness, no fuzzing.
13. **No IDN / punycode handling.** Internationalized domains are silently
    unsupported.
14. **StarC is a one-person language.** Open-sourcing this means the community
    contribution rate will be approximately zero — nobody can read the code
    without learning a language that has one user.
15. **MIT means anyone can fork and sell it.** That is the price of "MIT and
    forever free". If cloning is a real concern, the data/service layer needs a
    different license.
16. **Some sites break.** Killing ad scripts can leave layout holes or break
    lazy-loading logic that assumed the ad response would arrive. No per-site
    fallback exists yet.

### 5.3 The one-line summary

> Xin is *not* "the only ad blocker". Pi-hole (MIT) and AdGuard Home (GPLv3) have
> done local, proxy-free, free blocking for years. What is actually without
> precedent here is the **combination**: a self-defined binary container, a
> self-hosted matcher, a niche self-made language, and an architecture that
> happens to be immune to Manifest V3 — at sub-microsecond lookup cost.


## 7. Two modes

| Mode | What runs | What you see |
|---|---|---|
| `soft` | layer 1 only | ads never load, but **empty grey boxes remain** |
| `force` (default) | layer 1 + layer 2 | containers and "广告" labels are **removed entirely** |

Set in `data/mode.txt`; the extension can switch independently at runtime
(`chrome.storage`). Force is the default because "grey skeletons" look broken.

## 10. Disclaimer

Xin modifies `C:\Windows\System32\drivers\etc\hosts` when you run
`apply_hosts.ps1`. It backs nothing up automatically — **copy the file yourself
first**, and keep `restore_hosts.ps1` at hand. Blocking domains can break sites
that rely on them (login flows, CDNs, analytics-gated content). Use at your own
risk.
